# Remotion

> Scope: The scored composite Remotion adapter, its Media Parser and WebCodecs execution paths, and their framework-specific capability, normalization, lifecycle, telemetry, and runtime-applicability boundaries.
> Phase-2 owner: p2_engine_remotion.

## Purpose

This page specifies the Remotion [engine and adapter](../glossary.md) as it exists in the benchmark: one scored column assembled from `@remotion/media-parser` for inspection and sample extraction and `@remotion/webcodecs` for browser-native [WebCodecs](../glossary.md) decode, seek, conversion, and encoding. It answers which package executes each operation, what the column actually declares, and where the declared flat surface is broader than a concrete container/codec/options tuple.

It is the engine-specific companion to [engine-adapter contract](../subsystems/engine-adapter-contract.md), [runner and capability negotiation](../subsystems/runner-capability-negotiation.md), and [oracle system](../subsystems/oracle-system.md). Feature semantics live in the owning [demux](../features/demux.md), [remux](../features/remux.md), [transcode](../features/transcode.md), and [decode/seek](../features/decode-seek.md) pages.

The input and output container mappings are explicit: the conversion adapter can read the ten declared canonical containers but can only write MP4, WebM, or WAV. Its output codec mapper accepts H.264, HEVC/H.265, VP8, and VP9 for video; AV1 has no encoder mapping. AAC and Opus map directly, while all declared PCM output requests map to Remotion’s `wav` audio token, documented in the adapter as 16-bit PCM. MP3, FLAC, and Vorbis have no encode mapping. [src/engines/remotion-webcodecs/codecs.ts:18-92](../../src/engines/remotion-webcodecs/codecs.ts#L18-L92)

### Media Parser path

The parser’s source policy preserves the benchmark’s mutation semantics. Normal and HLS inputs use the original URL with Remotion’s `webReader`; mutated robustness inputs use `input.blob()` so corruption applied by the harness reaches the framework. [src/engines/remotion-media-parser/adapter.ts:273-294](../../src/engines/remotion-media-parser/adapter.ts#L273-L294)

Initialization imports `parseMediaOnWebWorker()` and makes a deliberately invalid warm parse. A parse-format rejection demonstrates a live worker, while a worker construction/transport failure changes the parser to its main-thread fallback. [src/engines/remotion-media-parser/adapter.ts:217-259](../../src/engines/remotion-media-parser/adapter.ts#L217-L259) A custom reader function cannot cross the worker message boundary, so every URL plus `webReader` operation deliberately executes `parseMedia()` on the main thread; only Blob inputs can use the worker path. The recorded `worker` flag reflects that per operation. [src/engines/remotion-media-parser/adapter.ts:296-328](../../src/engines/remotion-media-parser/adapter.ts#L296-L328)

Probe asks for duration, container, tracks, metadata, rotation, and FPS. HLS always goes through full demux; transport streams and ADTS can fall back to packet-derived fields; and a missing single-video FPS can trigger a slow full-file FPS parse. [src/engines/remotion-media-parser/adapter.ts:340-392](../../src/engines/remotion-media-parser/adapter.ts#L340-L392)

Demux installs asynchronous video and audio sample callbacks, turns each sample into `PacketInfo`, and requests a full parse. It assigns packet indices only after parsing by sorting video tracks before audio tracks and then by parser track id. [src/engines/remotion-media-parser/adapter.ts:411-498](../../src/engines/remotion-media-parser/adapter.ts#L411-L498) [src/engines/remotion-media-parser/adapter.ts:1226-1238](../../src/engines/remotion-media-parser/adapter.ts#L1226-L1238) Probe without a supplied canonical map preserves parser track order, whereas demux metadata is reordered to match the synthesized packet indices. [src/engines/remotion-media-parser/adapter.ts:545-591](../../src/engines/remotion-media-parser/adapter.ts#L545-L591)

Normalized tracks expose canonical video/audio labels, coded dimensions, rotation, FPS, sample rate, and channels. The parser path maps H.265 to `hevc`; its audio normalizer maps AAC to `aac` and leaves unsupported canonical families visible instead of fabricating a supported token. [src/engines/remotion-media-parser/codecs.ts:20-77](../../src/engines/remotion-media-parser/codecs.ts#L20-L77) [src/engines/remotion-media-parser/adapter.ts:1241-1297](../../src/engines/remotion-media-parser/adapter.ts#L1241-L1297) Container families are partly reconstructed from the input filename or MIME hint because Media Parser collapses [ISO BMFF](../glossary.md) to `mp4` and Matroska/WebM to `webm`. [src/engines/remotion-media-parser/codecs.ts:79-110](../../src/engines/remotion-media-parser/codecs.ts#L79-L110) [src/engines/remotion-media-parser/adapter.ts:1030-1033](../../src/engines/remotion-media-parser/adapter.ts#L1030-L1033)

Packet timestamps are rounded from Remotion’s microsecond [timebase](../glossary.md). Three adapter-side repairs then alter framework observations for specific goldens: duplicated TS/HLS AAC timestamps are reconstructed with 1024-sample steps; an [Annex B](../glossary.md) H.264 access-unit-delimiter byte is shifted between adjacent TS packets to match ffprobe packet sizes; and raw MP3 timestamps are rebuilt from MPEG frame sample counts. [src/engines/remotion-media-parser/adapter.ts:1036-1103](../../src/engines/remotion-media-parser/adapter.ts#L1036-L1103) [src/engines/remotion-media-parser/adapter.ts:1105-1154](../../src/engines/remotion-media-parser/adapter.ts#L1105-L1154) [src/engines/remotion-media-parser/adapter.ts:1156-1211](../../src/engines/remotion-media-parser/adapter.ts#L1156-L1211)

### WebCodecs path

Initialization dynamically imports both Remotion packages, the buffer writer, and the web reader, then best-effort warms a 64×64 H.264 `VideoEncoder` with hardware preference. A failed warm-up is ignored; the measured conversion later exposes any real support failure. Disposal only clears the imported-library handle. [src/engines/remotion-webcodecs/adapter.ts:265-294](../../src/engines/remotion-webcodecs/adapter.ts#L265-L294) [src/engines/remotion-webcodecs/adapter.ts:2302-2325](../../src/engines/remotion-webcodecs/adapter.ts#L2302-L2325)

`remux()` validates only the requested output-container token and calls the shared converter with no explicit per-track handler. The adapter’s own comment acknowledges that the framework default can copy a compatible track or re-encode when the destination cannot hold it. [src/engines/remotion-webcodecs/adapter.ts:462-474](../../src/engines/remotion-webcodecs/adapter.ts#L462-L474) Remotion’s official [track-transformation contract](https://www.remotion.dev/docs/webcodecs/track-transformation) also makes copy, re-encode, and remove distinct outcomes. Therefore the current method name does not enforce a copy-only remux invariant.

`transcode()` maps one output container, selects only `variants[0]` when a rendition ladder is present, rejects some requests, checks that requested track types exist, and builds codec/resize/rotation arguments. With both width and height it uses `max-height-width`, which fits inside the box while preserving aspect ratio rather than guaranteeing arbitrary exact dimensions. [src/engines/remotion-webcodecs/adapter.ts:485-540](../../src/engines/remotion-webcodecs/adapter.ts#L485-L540) [src/engines/remotion-webcodecs/adapter.ts:2285-2299](../../src/engines/remotion-webcodecs/adapter.ts#L2285-L2299) A WAV sample-rate request installs a forced audio re-encode at 128 kbit/s; explicit general video/audio bitrate options are otherwise not forwarded by this adapter. [src/engines/remotion-webcodecs/adapter.ts:511-540](../../src/engines/remotion-webcodecs/adapter.ts#L511-L540)

The shared converter first attempts a non-fatal metadata probe for duration and FPS sizing hints, creates a Remotion `webcodecsController`, invokes `convertMedia()` with an in-memory `bufferWriter`, saves the complete Blob, converts it to a `Uint8Array`, and then calls `remove()` to release the writer buffer. The controller is local and is not wired to the runner’s abort signal; `remove()` is reached only after conversion, save, and Blob copying succeed. The adapter does not expose `finalState` or progress telemetry. [src/engines/remotion-webcodecs/adapter.ts:543-603](../../src/engines/remotion-webcodecs/adapter.ts#L543-L603)

Frame decoding asks Media Parser for samples and creates a Remotion WebCodecs decoder from the parser track’s exact codec string, dimensions, description, and color space. It limits queue depth to 16, closes emitted `VideoFrame` objects after rasterization, sorts captured frames by presentation timestamp, and hashes tight RGBA. [src/engines/remotion-webcodecs/adapter.ts:605-695](../../src/engines/remotion-webcodecs/adapter.ts#L605-L695) [src/engines/remotion-webcodecs/digest.ts:32-74](../../src/engines/remotion-webcodecs/digest.ts#L32-L74) The callback is installed for every video track but the method keeps only one mutable decoder variable, so multi-video inputs are not isolated by track; decoder `flush()` rejection is swallowed. [src/engines/remotion-webcodecs/adapter.ts:620-682](../../src/engines/remotion-webcodecs/adapter.ts#L620-L682)

Seek creates a Media Parser controller, seeks to the best preceding keyframe, decodes forward, and retains the latest frame whose presentation timestamp is at or before the requested time, with a first-frame fallback. It has the same one-decoder-across-track-callback shape and swallowed flush rejection; no decoded frame becomes a generic error. [src/engines/remotion-webcodecs/adapter.ts:697-790](../../src/engines/remotion-webcodecs/adapter.ts#L697-L790)

### Oracle-facing consequences

The current result type has [`PASS`](../glossary.md), `FAIL`, the three `NA_*` statuses, `ERROR`, and `SKIPPED`, while each [oracle](../glossary.md) outcome is only `pass: boolean`; there is no current [`DIFF`](../glossary.md) representation. [src/core/scenario.ts:206-222](../../src/core/scenario.ts#L206-L222) The runner therefore converts every non-asset oracle false into cell `FAIL`, whether the mismatch means invalid media or merely a different valid representation. [src/core/runner.ts:1411-1447](../../src/core/runner.ts#L1411-L1447)

`golden-packets` groups packets by synthesized track index but still requires the same packet count, track-index layout, byte size, and keyframe bit, and only tolerates a constant per-track timestamp-origin shift plus a fixed drift bound. [src/core/oracles.ts:835-926](../../src/core/oracles.ts#L835-L926) That is especially consequential for this engine: its parser produces Annex B samples for TS/HLS and contains a one-byte access-unit-delimiter redistribution solely to match ffprobe’s packet-size accounting. [src/engines/remotion-media-parser/adapter.ts:1105-1154](../../src/engines/remotion-media-parser/adapter.ts#L1105-L1154) Annex B versus AVCC framing, in-band parameter sets, and legal NAL/access-unit grouping can change bytes and packet boundaries without changing decoded content, so the current comparator can turn a representation difference into `FAIL`.

For transform scenarios without committed frame goldens, `ssim-psnr` obtains the candidate by platform-decoding the engine output and obtains its neutral reference by independently platform-decoding the original source in the browser. [src/core/oracles.ts:1758-1808](../../src/core/oracles.ts#L1758-L1808) It samples up to eight frames and pairs candidate and reference strictly by array index. A changed FPS or frame count can therefore compare different presentation instants, and a valid output that the platform reference cannot decode is currently returned as `FAIL`. [src/core/oracles.ts:1905-1995](../../src/core/oracles.ts#L1905-L1995)

Exhaustive media mode preserves each input variant’s result and records `passed/admissible/total` coverage, but any per-file `FAIL` or `ERROR` collapses the aggregate cell to `FAIL` or `ERROR`. Thus “file 01 passes, files 02 and 03 fail” is stored in detail but has no first-class [partial coverage](../glossary.md) verdict. [src/core/runner.ts:1053-1115](../../src/core/runner.ts#L1053-L1115) [src/core/runner.ts:1118-1204](../../src/core/runner.ts#L1118-L1204)

## Target design and known gaps

### Target design

#### Tuple-aware capability and applicability boundary

Keep the composite registration, but make the public declaration and runtime validation describe [combinatorial support](../glossary.md), not just independent tokens. The tuple key must cover operation, input container, each input track codec/configuration, output container, each requested output codec, and options that alter feasibility: dimensions, FPS, bitrate, rotation, sample rate, channel count, rendition count, encryption, and resource/output mode. Remotion’s official [format-support matrix](https://www.remotion.dev/docs/media-parser/format-support) is the starting point for parser tuples, while its [WebCodecs integration guidance](https://www.remotion.dev/docs/media-parser/webcodecs) requires checking the exact `VideoDecoderConfig` or `AudioDecoderConfig`; the [WebCodecs specification](https://www.w3.org/TR/webcodecs/#codec-support) makes support configuration- and runtime-dependent.

The cleanup may extend `CapabilitySet` with tuple descriptors, but it must retain an operation-local runtime check because track configurations are unknown until parsing. A valid framework-level tuple that this adapter cannot execute must throw `NotApplicableError`, which the existing runner maps to `NA_ENGINE`. This applies to both Remotion children, including parser format/track combinations, copy-incompatible remuxes, exact decoder/encoder configurations, multi-track policies, unsupported transform options, and memory/output-mode limits. Filename heuristics are not acceptable evidence: inspect parsed tracks and exact codec configurations instead.

Use this classification at the adapter boundary:

| Observation | Required status or signal |
| --- | --- |
| Operation or broad capability is undeclared | Declaration-time `NA_ENGINE` |
| Valid input/option tuple is outside Remotion or this adapter’s implementation | Throw `NotApplicableError`; runner records `NA_ENGINE` |
| Remotion path exists but the browser cannot configure the exact WebCodecs decoder/encoder | Preflight/runtime browser-support signal; cell records `NA_BROWSER` |
| Malformed bytes in a robustness scenario are rejected cleanly | A graceful negative-test observation, not `NotApplicableError` and not harness `ERROR` |
| Adapter bug, invariant violation, or unexpected framework exception | `ERROR` with preserved cause and operation context |
| Valid, semantically equivalent output with a different representation | Oracle `DIFF` |
| Invalid output, missing required content, or semantic/tolerance violation | Oracle `FAIL` |

Acceptance requires table-driven positive and negative tests for every advertised container/codec direction and operation. Every negative test must assert `NA_ENGINE`, `NA_BROWSER`, graceful robustness, or `ERROR` explicitly; no unsupported valid tuple may depend on the disabled-cell list.

#### Copy-only remux

Implement remux with explicit per-track decisions. Before conversion, parse every track and use Remotion’s documented [track transformation](https://www.remotion.dev/docs/webcodecs/track-transformation) and copy-eligibility information. Return `copy` for every required track only when the destination supports it; if any required audio/video/other track would be re-encoded, removed, or implicitly converted, throw `NotApplicableError` before writing output. A copy-remux must preserve required track multiplicity, codec identity after alias canonicalization, sample timing/content, and program content. Silent video removal for an audio-only container and “remux by transcode” are `FAIL` if bytes were returned, not `DIFF`.

Verification must include compatible MP4→MP4 and WebM→WebM copy cases, cross-container tuples that cannot copy, multi-audio inputs, and WAV/audio-only destinations. Instrument per-track decisions (`copy`, `reencode`, `drop`, rejection) and assert that every successful remux records only `copy`.

#### Representation-aware packet and metadata evidence

Do not mutate Remotion’s packet sizes merely to reproduce ffprobe’s byte accounting. For AVC, the WebCodecs AVC registration defines a length-prefixed `avc` format when an `AVCDecoderConfigurationRecord` description is present and Annex B when it is absent; Annex B key chunks carry parameter sets in-band. [W3C WebCodecs AVC Codec Registration](https://www.w3.org/TR/webcodecs-avc-codec-registration/#encodedvideochunk-data) ISO BMFF also permits parameter sets in sample entries and, for suitable sample entries, in-band parameter sets. [W3C ISO BMFF byte-stream format note](https://www.w3.org/TR/mse-byte-stream-format-isobmff/#initialization-segments) Consequently, [AVCC](../glossary.md) versus Annex B, inline SPS/PPS, start-code width, and legal access-unit/NAL grouping can alter packet byte sizes and apparent keyframe accounting without altering decode semantics.

The target oracle model is three-way: `PASS` for the required semantic/structural contract, `DIFF` for a valid representation different from the ffmpeg-baked golden, and `FAIL` only for truly wrong output. Remotion packet evidence should expose raw framework observations plus enough framing metadata to normalize access units; representation diagnostics may record exact size/keyframe/grouping deltas, but those deltas alone cannot fail the cell. HEVC must use its analogous configuration-record versus Annex B rules rather than being mislabeled AVCC. [W3C WebCodecs HEVC Codec Registration](https://www.w3.org/TR/webcodecs-hevc-codec-registration/)

Metadata normalization should preserve both the framework’s canonical codec family and the underlying codec/configuration evidence. The oracle, rather than an engine-specific fudge, must treat AVC/HEVC/AAC aliases semantically; compare tracks by type rather than synthesized index; band [VFR and NTSC rates](../glossary.md); and widen duration for ISO BMFF [edit lists, encoder priming, and timebase rounding](../glossary.md). ISO/IEC 14496-12 defines the base format and edit-list timeline model. [ISO/IEC 14496-12:2022](https://www.iso.org/standard/83102.html) The AAC registration includes [HE-AAC/SBR](../glossary.md) and HE-AAC v2 with [Parametric Stereo](../glossary.md), so a core versus reconstructed sample-rate/channel view must not be “fixed” inside this adapter solely to match one golden. [W3C WebCodecs AAC Codec Registration](https://www.w3.org/TR/webcodecs-aac-codec-registration/)

Acceptance requires fixtures that present the same AVC access units as AVCC and Annex B, with SPS/PPS out of band and in band and with legal grouping changes. They must land `PASS` when observations normalize identically or `DIFF` when the golden representation differs, never `FAIL` from byte size alone. A dropped/corrupted access unit, wrong timing beyond tolerance, or missing random-access point remains `FAIL`.

#### Neutral reference decode and temporal pairing

Retain the source reference as a neutral, unscored in-browser WebCodecs decode: that separation is fair by design because it does not reuse the candidate Remotion decoder. Replace index pairing with timestamp-aware matching in the common presentation timeline, using the scenario’s cadence/tolerance and explicit policies for FPS conversion, duplicated/dropped frames, VFR, and rational NTSC rates. WebCodecs defines timestamps on encoded chunks and decoded frames, which provides the alignment key. [W3C WebCodecs specification](https://www.w3.org/TR/webcodecs/)

A valid candidate that the platform reference instrument cannot decode is not thereby wrong. Distinguish container invalidity from browser/reference codec unavailability: invalid or structurally unusable output is `FAIL`; valid output outside the browser reference’s exact configuration becomes `NA_BROWSER` with a diagnostic. Acceptance includes a deliberate FPS-change transcode, unequal frame-count cases, a VFR source, and a valid codec/configuration unavailable to the reference decoder.

#### Controllers, workers, cleanup, and telemetry

Propagate the runner abort/timeout signal into every active Remotion controller. Retain conversion and parser controllers for the duration of an operation, abort them on cancellation/disposal, and close every decoder, frame, worker, and writer buffer in `finally`. Remotion’s [WebCodecs controller](https://www.remotion.dev/docs/webcodecs/webcodecs-controller) exposes pause, resume, and abort; conversion results expose `remove()` and `finalState` through the official [`convertMedia()` contract](https://www.remotion.dev/docs/webcodecs/convert-media). Decoder flush failures must retain their cause rather than being swallowed.

Use worker execution only when the actual call can run there. Remotion documents that `parseMediaOnWebWorker()` cannot accept a custom reader because functions cannot be transferred to a worker. [Remotion `parseMediaOnWebWorker()`](https://www.remotion.dev/docs/media-parser/parse-media-on-web-worker) Record actual per-operation parse path, source reader, exact decoder/encoder configs and their support results, selected track ids, per-track copy/re-encode/drop decisions, queue high-water mark, controller final state, output bytes, and cleanup completion. Static “worker-capable” telemetry is insufficient.

Acceptance includes cancellation during parse, decode, seek, and conversion; forced save/copy/remove failures; multi-video and multi-audio inputs; and repeated runs checked for retained workers, decoders, frames, or writer buffers. The report must distinguish main-thread URL parsing from Blob worker parsing and must show that cleanup ran on success, `NA_ENGINE`, `NA_BROWSER`, `FAIL`, timeout, and `ERROR`.

#### Conformance and robustness grading

Replace broad Remotion disabled cells with executable conformance tests and runtime applicability decisions. Keep only narrowly justified, time-bounded quarantines for confirmed framework defects. Each retained skip must name the exact tuple, issue evidence, and removal condition.

Exhaustive robustness results must preserve partial coverage as a first-class grade. “File 01 passes, files 02 and 03 fail” is useful compatibility evidence, not an adapter `ERROR`; individual malformed-file rejection remains visible, while unsupported *valid* files become `NA_ENGINE`. The reporting policy is owned by [reporting and aggregation](../subsystems/reporting-aggregation.md), but Remotion must provide the typed causes that make that grading possible.
