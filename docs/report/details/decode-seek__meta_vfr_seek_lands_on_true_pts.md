## Why the winner wins (deep technical)
The operation is a **precision seek into an H.264 elementary stream carried in an MP4 with a variable frame rate (VFR)**. VFR is the trap here: the stts (decode-time-to-sample) table has irregular per-sample deltas, so the real presentation timestamps do NOT sit on a nominal-fps grid. The scenario requests `tUs=4_250_000` with `expectKeyframe:false` and a generous `seekToleranceUs=250_000` (src/scenarios/decode-seek/index.ts:716-728). The metamorphic invariant `vfr-seek-lands-on-true-pts` deliberately uses that wide tolerance to expose engines that "cheat" by snapping to a computed grid point rather than landing on an actual demuxed frame pts. The golden video-packet PTS table contains a real frame at **4233333µs** (the nearest true sample to 4.25s); the correct answer is to decode to and return exactly that pts.

The oracle (src/core/oracles.ts:3571-3615, `vfrSeekLandsOnTruePtsInvariant`) computes two independent quantities: `expectedPtsUs = nearestPacketPts(videoPkts, requestedUs)` (the nearest real pts to the request) and `landedActualDeltaUs = minPacketPtsDelta(videoPkts, seek.landedPtsUs)` (how far the engine's landed pts is from ANY real demuxed pts). It fails if either `targetDeltaUs` (landed vs expected) or `landedActualDeltaUs` (landed vs nearest-real) exceeds the tolerance. The second check is the anti-grid-snap guard: an engine can be inside tolerance on `targetDeltaUs` yet still report a pts that does not correspond to any real frame.

mediabunny scored the strongest possible result on both axes: `landedPtsUs=4233333`, `expectedPtsUs=4233333`, `targetDeltaUs=0`, `landedActualDeltaUs=0`. It returned the exact true VFR frame pts, with zero error. Mechanistically this is because mediabunny's seek adapter (src/engines/mediabunny/adapter.ts:1415-1436) constructs a `VideoSampleSink` over the primary video track and calls `sink.getSample(targetSec)` (line 1421-1423). Per mediabunny's documented contract (adapter comment lines 1413-1414), `getSample` returns the last frame whose start ≤ t in presentation order — i.e. the actually-decoded sample visible at that timestamp — and the adapter reports `landedPtsUs = sample.microsecondTimestamp` (line 1426), the decoder's real frame timestamp, not a recomputed grid value. Because mediabunny indexes the true sample table and decodes the real frame, the returned pts is by construction a genuine demuxed pts; on this VFR clip that is 4233333µs. The backend used (env.configUsed) was **WebCodecs with prefer-hardware** (`backend:"webcodecs"`, `hwAccel:"prefer-hardware"`, `pipeline:"streaming-lockstep"`, `coopCoep:"not-required"`, `wasmThreads:0`), so the actual frame decode rode the Apple M1 Max hardware H.264 decoder — which is why its wall (46.905ms) and long-task budget (183ms) are an order of magnitude tighter than the wasm engines.

web-demuxer tied mediabunny on correctness exactly (Δtarget=0, Δactual=0, landed 4233333µs) — both are bit-equal on the invariant. The tie therefore drops to performance (task rule 4b). mediabunny's wall median is **46.905ms vs web-demuxer's 135.995ms = 2.90x faster**, and its blocking work is **183ms vs 5137ms long-tasks = ~28x less main-thread stall**. Both ran on a single sample (n=1, mad=0), so the spread is unmeasured and the perf margin is point-estimate evidence — but the gap (2.9x wall, 28x long-tasks) is far larger than plausible single-run jitter, so the ranking is robust. peakMemory was not sampled for mediabunny (n=0), so it cannot be used as a discriminator.
