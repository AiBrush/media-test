## Verdict

- Best framework: **web-demuxer@4.0.0** (engineId `web-demuxer@4.0.0`).
- Contested: **YES** — all 7 engines PASS the single gating oracle `golden-packets` with the identical, correct result (measuredCount 2308 == goldenCount 2308, comparedTracks 2). Correctness is therefore a tie, so the decision falls to performance.
- Decisive factor: **wall-clock median**. web-demuxer = **5.5 ms** is the lowest of all 7. Runner-up by wall is remotion-media-parser@4.0.479 = **18.995 ms**.
- Margin over runner-up: web-demuxer is **~3.45x faster wall** than remotion-media-parser (18.995 / 5.5), **~15.6x** faster than mediabunny (85.89 / 5.5), **~29.8x** faster than ffmpeg.wasm (163.755 / 5.5), **~42.9x** faster than mp4box (235.675 / 5.5), and ~607x / ~1094x faster than remotion-webcodecs (3338.69) / platform (6014.72).
- CAVEAT (see Anti-cheat): the web-demuxer winner and the remotion-media-parser runner-up both take an **adapter-local MP4 sample-table fast-path** for this exact (hardcoded) asset, NOT their nominal library's packet reader. The PASS is genuine (real moov parse of the real file), but the wall numbers measure a hand-written box parser, not the FFmpeg/WASM library. This makes the perf-based win a WEAK-GATE result.

## Why the winner wins (deep technical)

The operation is **demux of a faststart H.264-in-MP4 (avc1) + AAC (mp4a)** container; the oracle wants only the structural packet table — per-track index, size, pts/dts in µs, keyframe flag — which for an ISO-BMFF faststart file is fully described by the `moov` sample tables (`stsz` sizes, `stts` durations, `ctts` composition offsets, `stss` sync samples) and requires **no `mdat` payload read and no decode**.

web-demuxer's adapter recognizes this and routes the call through a narrow fast-path: `demux()` at `src/engines/web-demuxer/adapter.ts:765-767` calls `shouldUseProgressiveMp4SampleTableFastPath(input)` and, when true, returns `demuxProgressiveMp4SampleTable(input)`. The gate is `src/engines/web-demuxer/mp4-sample-table.ts:39-41`, which fires only for a hardcoded asset set containing `'h264_1080p_30s.mp4'`. The implementation (`mp4-sample-table.ts:48-190`) does a real ISO-BMFF parse:
- `readMoovBox` (`:68-89`) issues an HTTP `Range: bytes=0-65535` read, walks top-level boxes, finds `moov`, then ranges exactly the moov bytes — so only ~tens of KB cross the wire, never the 31 MB file or the `mdat`.
- `sampleTableFromTrak` (`:139-190`) parses `stsz`/`stts`/`ctts`/`stss` and synthesizes one `PacketInfo` per sample: `size = sizes[i]`, `dtsUs = ticksToUs(dtsTicks)`, `ptsUs = ticksToUs(dtsTicks + ctts[i])`, `keyframe = stss.has(i+1)` (or all-true when `stss` absent). The header comment explicitly states it "never reads mdat and never fabricates packets from duration or fps" (`:10`).

Because it touches only the moov over a single small Range request and runs pure synchronous byte math, it lands at **5.5 ms wall** — far below any engine that actually streams the elementary packets. That is the mechanistic reason for the win: it does the minimum I/O the oracle's contract permits, while every losing engine pays for either real packet streaming or codec configuration.

The oracle confirms correctness rather than a shortcut: `goldenPackets` (`src/core/oracles.ts:703-796`) compares the engine's packet table against the committed ffprobe golden — exact packet count, exact per-track `trackIndex` multiset (`sameLayout`), exact `size` and `keyframe` per sample, and pts/dts within ±1ms after a constant per-track origin alignment (the alignment absorbs the AAC priming shift; golden's first audio packet is pts -21333µs). web-demuxer's run reports `measuredCount 2308`, `goldenCount 2308`, `comparedTracks 2`, `maxPtsDriftUs 1` — a near-bit-exact structural match (the 1µs is sub-tolerance rounding of the µs conversion).

## What each other framework did wrong

- **remotion-media-parser@4.0.479** (runner-up, 18.995 ms): PASS, identical golden-packets result (2308, drift 1µs). Lost purely on wall — ~3.45x slower than web-demuxer. Mechanistically it takes the SAME class of fast-path: `adapter.ts:437-449` calls `shouldUseMp4SampleTableDemux(input)` (hardcoded set includes `'h264_1080p_30s.mp4'`, `mp4-sample-table.ts:21-22,57-58`) and parses moov tables itself; its extra cost is a separate `probe()` pass before `demuxMp4SampleTable`. Same correctness, marginally heavier path.
- **mediabunny@1.48.0** (85.89 ms): PASS, 2308/drift 1µs. ~15.6x slower than the winner because it runs its genuine `streaming-lockstep` packet pipeline (configUsed.pipeline) over the file rather than a moov-only shortcut. Correct and honest, but pays real streaming cost.
- **ffmpeg.wasm@0.12.15** (163.755 ms): PASS with the *strongest* numeric drift (`maxPtsDriftUs 0`, exact) — the only engine that hit zero drift. Lost on wall (~29.8x slower): the FFmpeg-in-WASM demuxer parses the container in the wasm worker, a single-thread (wasmThreads 0) cost the moov fast-path avoids.
- **mp4box@2.3.0** (235.675 ms): PASS, 2308/drift 1µs. configUsed shows pure-js whole-file append (`whole-file-append(MP4BoxBuffer+fileStart)`, rangeReads:false) — it buffers/appends the whole file before emitting samples, the slowest of the genuine-parse demuxers; ~42.9x slower than the moov-Range fast-path.
- **remotion-webcodecs@4.0.479** (3338.69 ms): PASS, 2308/drift 1µs, but ~607x slower. Its `streaming-backpressure` WebCodecs convert pipeline is built for decode/transcode rows; for a pure packet-table demux it is heavyweight overkill. Correct, badly mismatched to the op.
- **platform@chrome-149** (6014.72 ms): PASS, 2308/drift 1µs, slowest at ~1094x. The platform path drives a `VideoDecoder`/`<video>` based pipeline (configUsed.decode `VideoDecoder`); enumerating packets through the browser media stack is enormously more expensive than a moov parse.

No engine returned NA or FAIL — every framework can demux H.264/AAC MP4, so this scenario is a pure performance spread over a shared-correctness baseline.

## Anti-cheat validation

- Scenario definition: `src/scenarios/demux/index.ts:66` — `{ asset: 'h264_1080p_30s.mp4', container: 'mp4', videoCodecs: ['h264'], audioCodecs: ['aac'] }`, expanded at `:256-274` with `op:'demux'`, `oracles:['golden-packets']`, `metrics:['wall']`. The file header (`:1-31`) documents golden-packets as the structural gate baked from ffprobe.
- Fixture: `fixtures/media/h264_1080p_30s.mp4` EXISTS, **31 MB** real MP4 (not synthetic/empty/mock). Golden `fixtures/golden/h264_1080p_30s.mp4.packets.json` exists (264 KB), 2308 packets, track layout {0:video 900, 1:audio 1408}, first audio pts -21333µs, 1423 keyframes — physically plausible for 30s 30fps H.264 + AAC.
- Oracle: `golden-packets` at `src/core/oracles.ts:703-796` — a REAL comparison: exact count, exact per-track layout (`sameLayout`), exact per-sample size + keyframe flag, pts/dts within ±1ms after constant per-track origin alignment. Not trivially satisfiable (count/size/keyframe must match exactly; only a constant timestamp offset is tolerated, varying residual fails). The winner's measurements (2308/2308, comparedTracks 2, maxPtsDriftUs 1) are consistent with a true parse.
- Winner adapter: `src/engines/web-demuxer/adapter.ts:764-767` -> `src/engines/web-demuxer/mp4-sample-table.ts:48-190`. It performs a genuine moov/stbl parse over HTTP Range and does NOT return canned output, copy a golden, or swallow errors (it throws on missing moov/stbl/stsz). NOT a golden short-circuit.
- **Verdict: WEAK-GATE.** Two concerns combine. (1) The winner does NOT exercise the web-demuxer FFmpeg/WASM packet reader for this asset; `shouldUseProgressiveMp4SampleTableFastPath` (`mp4-sample-table.ts:39-41`) hardcodes `'h264_1080p_30s.mp4'` into an adapter-local box parser, so the 5.5 ms wall measures the adapter's own code, not the library under test. The runner-up (remotion-media-parser) does the same via `shouldUseMp4SampleTableDemux` (`adapter.ts:437`). The PASS and the packet table are real, but the perf-based ranking attributes a hand-written parser's speed to the library — a misleading-but-not-fabricated result. (2) Only a single oracle (golden-packets) gates, and only `wall` is measured (n==1), so there is no peakMemory/longtasks check to catch a non-lazy read; the gate is correctness-real but evidence-thin.
- Cached note: the winner's result has **cached==true** ("cached previous PASS result") — it was reused, not freshly re-run. Per the launcher-seeding caveat, stale-PASS reuse is a known risk; the 5.5 ms figure should be treated as a prior run's measurement, not a fresh one. All 7 engines are cached==true here.

## Confidence & caveats

- Confidence: **medium**. Correctness for all engines is real and unanimous (2308 packets, drift 0-1µs against an independent ffprobe golden). The ordering is robust at the gross level (the winner is orders of magnitude ahead), but the specific winner-vs-runner-up margin (3.45x) rests on n==1 cached timings (mad==0, no spread) AND on the fact that both fast-paths are adapter-local parsers, so the comparison is "whose hand-written moov parser is leaner" rather than "whose library demuxes fastest."
- If the goal is "which LIBRARY demuxes H.264/AAC MP4 fastest," the honest winner among genuine-library paths is **mediabunny (85.89 ms)**, then ffmpeg.wasm (163.755 ms, drift 0), then mp4box (235.675 ms) — web-demuxer and remotion-media-parser's fast-path numbers are not comparable to those.
- All numbers are cached; a fresh run (clearing raw + .browser-cache) is advisable before publishing the 5.5 ms headline.
