## Why the winner wins (deep technical)

This is a pure demux (packet-enumeration) scenario over an H.264/AAC QuickTime MOV. The operation is "walk the container, emit every elementary-stream packet with its size, presentation timestamp, decode timestamp and keyframe flag." There is no pixel decode in the gating path, so the contest is entirely about how cheaply a library can parse the MOV box structure (`moov`/`stts`/`stsz`/`stsc`/`stco`/`stss`) and stream out the sample table.

mediabunny ran with `backend: "webcodecs"`, `coreBuild: "pure-ts-esm"`, `pipeline: "streaming-lockstep"`, `sharedArrayBuffer: false`, `coopCoep: "not-required"` (env.configUsed). Crucially, for demux it never touches a decoder: its adapter (`src/engines/mediabunny/adapter.ts:1152-1183`) opens the input once, calls `getTracks()`, then for each track constructs an `EncodedPacketSink` and iterates `sink.packets(undefined, undefined, { verifyKeyPackets: true })`, pushing `{ trackIndex, size: pkt.byteLength, ptsUs: pkt.microsecondTimestamp, dtsUs: ptsUs, keyframe: pkt.type === 'key' }` (adapter.ts:1162-1176). This is mediabunny's native pure-TS MOV sample-table reader producing `EncodedPacket` objects directly from the container index — no WASM module to instantiate, no decoder warmup. That absence of fixed startup cost is what produces the 15.03 ms wall: roughly 2.25x under WebCodecs-backed `platform` and ~1.5x under ffmpeg.wasm, which both pay container-parse plus framework setup, and ~12-44x under the remotion stack and web-demuxer.

The oracle measurements confirm the parse is correct, not just fast: `measuredCount: 386`, `goldenCount: 386`, `comparedTracks: 2`, `maxPtsDriftUs: 1`. The golden (`fixtures/golden/h264_1080p_5s.mov.packets.json`) is real ffprobe output — its first audio packet carries the raw container priming pts `-21333µs` while later packets step at the AAC frame cadence (`+21333µs`). The oracle (`src/core/oracles.ts:703-796`) groups packets per track, sorts by dts/pts, and compares position-by-position with **exact** size and keyframe-flag equality, allowing only a single constant per-track origin shift for timestamps (because mediabunny applies the edit list and starts at 0 while ffprobe exposes the raw negative priming). mediabunny's residual after that origin alignment is 1µs (rounding), well inside the 1ms tolerance — meaning it reproduces every sample size and keyframe boundary of both the H.264 and AAC tracks bit-for-bit in count and structure.

So the winner edge is mechanistic: identical, maximal correctness across all seven engines, and mediabunny achieves it with the lowest fixed cost because its demux path is a zero-decode, no-WASM, no-COOP/COEP, pure-TS sample-table walk over the MOV index.

## What each other framework did wrong

- **mp4box@2.3.0** — PASS, lost on speed only. Identical correctness (386/386, drift 1µs) but `backend: pure-js` with `whole-file-append(MP4BoxBuffer+fileStart)` and `rangeReads:false` buffers the whole 4.4 MB file before emitting samples; 22.43 ms = 1.49x slower than mediabunny.
- **platform@chrome-149** — PASS, runner-up on speed. WebCodecs backend with hwAccel, but the demux still routes through the browser's MP4 parse + `VideoDecoder` setup path; 33.77 ms = 2.25x slower. Same correctness (drift 1µs).
- **ffmpeg.wasm@0.12.15** — PASS, drift 0µs (slightly tighter than the winner) but 37.09 ms = 2.47x slower; the single-thread WASM module instantiation and FS round-trip dominate a task this small. Correctness equal/marginally better; speed loses.
- **remotion-media-parser@4.0.479** — PASS, `backend: cpu-js` `fieldsTier: full-parse(demux)` on the main thread; 189.51 ms = 12.6x slower. Correct (drift 1µs) but the JS full-parse is far heavier per packet.
- **remotion-webcodecs@4.0.479** — PASS, `streaming-backpressure` with `bufferWriter` and queue-wait; 334.20 ms = 22.2x slower. The conversion-oriented pipeline carries overhead irrelevant to a pure packet walk.
- **web-demuxer@4.0.0** — PASS, slowest at 664.89 ms = 44.2x slower. Drift 0µs (correct), but its WASM ffmpeg-derived demuxer pays the largest setup/teardown for a 5 s clip.

All six non-winners are honest PASSes; none is NA or FAIL. The only differentiator is wall time.

## Anti-cheat validation

- Scenario definition: `src/scenarios/demux/index.ts:101` — `{ asset: 'h264_1080p_5s.mov', container: 'mov', videoCodecs: ['h264'], audioCodecs: ['aac'] }`. No explicit `id`, so the suite derives `demux/h264_1080p_5s`. Real input.
- Fixture: `fixtures/media/h264_1080p_5s.mov` exists, 4.4 MB — a genuine H.264/AAC MOV, not synthetic/empty/mock.
- Golden: `fixtures/golden/h264_1080p_5s.mov.packets.json` exists (43 KB), real ffprobe packet table with physically plausible values (303/416/322-byte AAC packets, 44366-byte H.264 IDR keyframe, raw priming pts -21333µs, AAC cadence +21333µs).
- Oracle: `src/core/oracles.ts:703-796` (`goldenPackets`). Performs a real per-track, position-by-position comparison requiring exact packet count (386), exact track-layout multiset, exact per-packet size, exact keyframe-flag, and timestamp match within 1ms after only a single constant per-track origin shift. Not trivially satisfiable; no smoke/proxy fallback for this container.
- Winner adapter: `src/engines/mediabunny/adapter.ts:1152-1183`. Genuinely iterates `EncodedPacketSink.packets()` with `verifyKeyPackets: true`, reading real `byteLength`/`microsecondTimestamp`/`type` from the live mediabunny container reader. No canned output, no input→output copy, no golden short-circuit, no error swallowing (try/finally only disposes the input).
- Cached note: mediabunny's result has `cached: true` ("cached previous PASS result") — and in fact ALL 7 engines are cached. The PASS verdicts and 386-packet measurements are reused from a prior run, not freshly re-executed in this report pass; per the launcher seeding caveat, wall numbers are stale-but-representative. Correctness conclusion is unaffected (deterministic packet table); the speed ranking carries normal single-shot + cache-staleness uncertainty.
- Verdict: **REAL** — real fixture, real mediabunny demux implementation, meaningful exact-comparison oracle. The only soft spot is that evidence is cached and n=1, which lowers confidence on the precise speed margin (not on who wins).
