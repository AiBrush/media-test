## Why the winner wins (deep technical)

This is a pure read-side metadata probe on H.264 video + AAC audio in a faststart MP4 (golden meta: container `mp4`, durationSec 30, video h264 1920x1080 @ 30 fps, audio aac 48000 Hz / 2 ch). The operation never decodes a frame; it only needs to parse the `moov` atom (mvhd duration, two `trak`/`stsd` entries) and emit normalized track metadata. Correctness is therefore trivial for any competent demuxer, and the contest reduces to how cheaply each engine reaches the moov.

mediabunny's adapter takes the cheapest possible path. In `metadataFromInput` (src/engines/mediabunny/adapter.ts:417) it calls `input.getDurationFromMetadata()` FIRST (adapter.ts:429), which reads the container's declared duration straight out of the `mvhd` box WITHOUT scanning samples; only if that returns null/non-finite does it fall back to the expensive `computeDuration()` full-fragment walk (adapter.ts:434-441). For a faststart MP4 with a precise mvhd duration, the cheap path always succeeds, so mediabunny pays nothing for the duration. Track metadata comes from `input.getTracks()` + `normalizeTrack()` (adapter.ts:443-447, normalizeTrack at adapter.ts:297) reading the `InputVideoTrack`/`InputAudioTrack` getters straight off the stsd — again no sample scan. The source is a `BlobSource` opened by `openInput` (adapter.ts:245) with the format set restricted to the asset's container (adapter.ts:249-273), so mediabunny does not even probe other format singletons. Pure-TS ESM core, no wasm instantiation, no WebCodecs warm-up on the timed path → 4.325 ms wall. Its `env.configUsed` shows backend `webcodecs` / `coreBuild:pure-ts-esm` / `sharedArrayBuffer:false` / `coopCoep:not-required`, but for a probe the WebCodecs decoder is never engaged.

The oracle measurement confirms an exact result, not a loose pass: `golden-metadata` reported `durationDeltaSec:0` against `durationToleranceSec:0.0417` and "metadata matches golden (2 track(s))" — duration is bit-on with the golden 30.0 s and both the h264 and aac tracks matched codec/dims/fps/sampleRate/channels positionally (goldenMetadata at src/core/oracles.ts:595, compareTrack at oracles.ts:659).

- **remotion-webcodecs@4.0.479** — PASS, identical oracle result. 26.27 ms = 6.1x slower than mediabunny. It is the WebCodecs convert wrapper (`pipeline:streaming-backpressure`, bufferWriter) and carries more setup/parser overhead than the bare media-parser for a metadata-only read.
- **web-demuxer@4.0.0** — PASS, identical oracle result. 33.44 ms = 7.7x slower. wasm-backed libav demuxer; pays wasm-call and module overhead to reach the same moov fields.
- **mp4box@2.3.0** — PASS, identical oracle result. 177.54 ms = 41x slower. `pipeline:whole-file-append(MP4BoxBuffer+fileStart)`, `rangeReads:false` → it buffers/appends the whole 31 MB file through MP4Box.js before `onReady` fires, so it pays full-file ingestion cost just to read the moov.
- **ffmpeg.wasm@0.12.15** — PASS, identical oracle result. 202.01 ms = 47x slower. Heavyweight wasm ffprobe-style path; module + filesystem-write overhead dominates a trivial metadata read.
- **platform@chrome-149** — PASS, identical oracle result, but 5942.15 ms = 1374x slower. The platform path uses `<video>`/MediaSource-style demux+decode plumbing (`decode:VideoDecoder`, `encode:<video>→canvas→MediaRecorder`); for a metadata probe it spins up far more machinery (element load, possibly full media-element readiness) than a header parse needs. Correct but catastrophically slow for this operation.
