## Why the winner wins (deep technical)

The operation is a metadata probe of a 5-second 1920x1080 H.264 (video) + 48 kHz stereo AAC (audio) stream muxed in a QuickTime MOV (`major_brand: "qt  "`). A correct probe must report container=`mov`, durationSec≈5, two tracks (video h264 1920x1080 @30fps, audio aac 48000/2) by reading the `moov` box (and its `mvhd`/`trak`/`stsd` children) WITHOUT decoding any frames. The fixture has B-frames-style GOP semantics typical of H.264, but probe must surface dims/duration from the container header, not from decode order.

Why remotion-media-parser is the right tool: its adapter declares ONLY `probe` and `demux` capabilities (`src/engines/remotion-media-parser/adapter.ts:188-191`) and its `probe()` (`adapter.ts:348-417`) calls `parseMedia` requesting the minimal fast field set — `durationInSeconds, container, tracks, metadata, rotation` (and `fps` only when not already derivable) — tagged `fieldsTier: 'metadata-only'` (`adapter.ts:374-384`). For a faststart MOV the parser reads the header region and stops; it never streams the mdat sample payload. This is the minimum-work path for a probe and is why it lands at 8.44 ms on `backend:"cpu-js"` with `hwAccel:false`, `worker:false`, no SharedArrayBuffer, no COOP/COEP.

remotion-webcodecs (8.22 ms) is functionally the same engine for this op: its `probe()` (`src/engines/remotion-webcodecs/adapter.ts:332-360`) also calls `mp.parseMedia({ fields: { container, durationInSeconds, tracks, metadata, ... } })`, and the adapter explicitly states it "drives the IDENTICAL parseMedia read path" as the media-parser adapter (`adapter.ts:257`). It carries WebCodecs/GPU machinery (`backend:"webcodecs"`, `hwAccel:"prefer-hardware(+software fallback)"`) but none of that is exercised for a header-only probe, so the two converge to within 0.22 ms — indistinguishable at n=1. Hence the contest reduces to "same parser, different wrapper," and the metadata-only specialist is the cleaner attribution of the win.

The oracle confirms correctness is uniform, not a differentiator: `goldenMetadata` (`src/core/oracles.ts:595-657`) compares container string, duration within a per-frame band, and every track positionally (type/codec/width/height/fps/sampleRate/channels via `compareTrack`, `oracles.ts:659-686`). Every engine returned `durationDeltaSec = 0` against golden duration 5s with tolerance 0.041667s (= 1/24 s, the strict ~1-frame band for a precise container), and matched the 2-track layout — so no engine had any correctness edge. The race is purely how cheaply each library reaches the `moov`.

## What each other framework did wrong

- **remotion-webcodecs@4.0.479** (PASS, runner-up): correct, 8.22 ms — nominally 0.22 ms faster, but on n=1 with mad=0 this is noise, and it runs the identical `parseMedia` path while dragging unused WebCodecs/hardware-decoder setup; not a meaningful performance win.
- **mp4box@2.3.0** (PASS): correct but slower at 10.09 ms (1.2x slower). Its `pipeline:"whole-file-append(MP4BoxBuffer+fileStart)"` with `rangeReads:false` appends/parses more of the file than a header-only reader, even with `discardMdatDataProbe:true`.
- **mediabunny@1.48.0** (PASS): correct but slowest of the fast tier at 10.62 ms (1.29x slower). `pipeline:"streaming-lockstep"` pure-TS demux costs more setup than media-parser's metadata-tier read.
- **ffmpeg.wasm@0.12.15** (PASS): correct but 25.31 ms (3.1x slower). The wasm module must be invoked and the MOV fed through libavformat's demuxer; even a metadata probe pays the wasm boundary + single-thread cost.
- **web-demuxer@4.0.0** (PASS): correct but 32.40 ms (3.9x slower) — slowest of the wasm-backed group; libav-in-wasm demux init dominates the probe.
- **platform@chrome-149** (PASS): correct but 5999.99 ms (~710x slower). The platform adapter's "encode/playback" pipeline (`encode:"<video>→canvas→MediaRecorder(out)"`) drives a near real-time path; 6.0 s for a 5 s clip indicates it effectively plays the media rather than reading the header. It still passes golden-metadata (`durationDeltaSec 0.021333s` < tol), but it is catastrophically wrong as a *probe* implementation in terms of cost — a header read should be milliseconds, not seconds.

## Anti-cheat validation

- Scenario definition: `src/scenarios/probe/index.ts:98` — `{ asset: 'h264_1080p_5s.mov', container: 'mov', videoCodecs: ['h264'], audioCodecs: ['aac'] }`. Generated via the probe-matrix factory in this file (no per-asset `notes`/override for this row; it uses default strict tolerances).
- Fixture: `fixtures/media/h264_1080p_5s.mov` EXISTS, 4.4 MB — a real H.264/AAC MOV, not synthetic/empty/mock. Goldens present and substantive: `h264_1080p_5s.mov.meta.json` (container mov, dur 5s, 1920x1080 h264 @30fps + 48000/2 aac), plus `.packets.json` (43k), `.ssim.json` (76k), `.frames.json` — i.e. real decoded references exist for this asset.
- Gating oracle: `golden-metadata` at `src/core/oracles.ts:595-657`. It performs a REAL field-by-field comparison against the golden meta JSON (container, duration within a derived per-container tolerance, positional per-track codec/dims/fps/sampleRate/channels). Not trivially satisfiable: duration band here is the strict 0.041667s (~1 frame), and measured `durationDeltaSec=0` shows an exact match, not a wide-tolerance pass. Measurements are physically plausible (1920x1080, 30fps, 48kHz/2ch, 5s) and match the golden exactly.
- Winner adapter: `src/engines/remotion-media-parser/adapter.ts:348-417` (`probe()`), calling `parseMedia` with a real metadata field set (`adapter.ts:374-384`). No canned output, no copy-input-to-output, no short-circuit to golden, no error swallowing — it genuinely parses the MOV header via @remotion/media-parser.
- Verdict: **WEAK-GATE**. The implementation and fixture are real and the comparison is a genuine exact-match, but the ONLY gating oracle for this scenario is `golden-metadata` (a structural/metadata check). No bit-exact or decoded-frame oracle gates this probe, so a PASS proves "header fields correct," not pixel/packet fidelity. That is appropriate for a probe op but it is a metadata-strength gate, not a strong correctness gate — hence WEAK-GATE rather than REAL. The PASS itself is honest.
- Cached note: ALL 7 engine results have `cached==true` ("cached previous PASS result"). The evidence is reused from a prior run, not freshly re-executed in this report run — staleness risk applies to the exact wall numbers (especially the razor-thin 8.22 vs 8.44 ms ordering). Per project memory, stale PASS reuse can mask drift; a fresh run (clear raw + .browser-cache) would be needed to confirm the winner ordering.

## Confidence & caveats

- Confidence: **medium**. Correctness uniformity (all PASS, all durationDeltaSec=0) is unambiguous. The winner ordering is fragile: the top two are the same underlying parser within 2.7% on n=1, mad=0, and all data is cached. Any of the top-4 (both remotion engines, mp4box, mediabunny) could plausibly top a fresh re-run.
- Caveats: (1) bench captured only `wall`; no memory/throughput/longtask metrics to break the tie on a secondary axis. (2) cached==true everywhere — numbers are reused. (3) platform's 6s wall is a probe anti-pattern but still passes the metadata gate, illustrating why a metadata-only gate is a WEAK-GATE for ranking probe *implementations*. (4) The remotion-webcodecs vs remotion-media-parser distinction is essentially a labeling choice given the shared parseMedia path.
