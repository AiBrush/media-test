## Why the winner wins (deep technical)

**The operation.** This is a lossless container re-wrap: take the H.264 video samples and AAC audio samples out of a Matroska (MKV) container and re-pack them into a QuickTime (MOV / ISOBMFF) container, with no re-encode. Codec legality is the whole premise (matrix.ts:9-15): H.264 (avc) and AAC are legal in both MKV and MOV, so only the wrapper changes. Mechanically the engine must (1) parse Matroska EBML/SimpleBlock framing and lacing, (2) preserve the already length-prefixed (AVCC) H.264 NAL framing — MKV stores H.264 length-prefixed exactly like ISOBMFF, so unlike the MKV->TS sibling cell there is no Annex-B start-code rewrite, just a re-table of sample sizes/offsets into `stsz`/`stco`/`stsc` and a `moov`/`stbl` build — and (3) write a valid `ftyp`/`moov`/`mdat` MOV with a faststart-style layout that the reference engine can re-import.

**Both PASS engines are genuine stream-copies, with identical correctness evidence.** The single gating oracle is `reference-reimport` (default for every remux cell, _shared.ts:78-81). For an `op:'remux'` scenario this oracle (oracles.ts:1225-1271 dispatching to `semanticRemuxReimport`, oracles.ts:1273-1324) re-imports the engine's output bytes with the *reference* engine's `demux()` and checks: non-empty packet table, media-track count vs golden, per-(type,codec) track layout, and duration within tolerance. Both engines returned **identical** structural results: `reimportPackets:770`, `reimportKeyframes:475`, `reimportMediaTracks:2`, `goldenMediaTracks:2`. The golden meta (h264_in_mkv.mkv.meta.json) confirms exactly 2 media tracks (video h264 1280x720@30, audio aac 48 kHz stereo) and durationSec 10.021. Duration delta was 0.016 s (mediabunny) and 0.005 s (ffmpeg.wasm), both far under the 0.1 s floor tolerance (oracles.ts:1318). So on the correctness ladder both sit at the same rung (structural/metadata-exact via `reference-reimport`); neither has an edge there, which forces the decision onto performance.

**Why mediabunny is faster here.** mediabunny ran on `backend: webcodecs`, `pipeline: streaming-lockstep`, `coreBuild: pure-ts-esm`, `coopCoep: not-required`, `sharedArrayBuffer: false` (env.configUsed). Its `remux()` (adapter.ts:1244-1260) takes the pure stream-copy path: with no `fastStart:'reserve'`, no codec/transform options, it opens the input, builds an `Output` with the MOV format, and calls `runConversion` (adapter.ts:842-868). Because no `video`/`audio` transform options are attached, mediabunny's `Conversion` copies the encoded samples directly — no `VideoDecoder`/`VideoEncoder` is instantiated for a plain remux, so the WebCodecs backend is effectively unused for the copy itself; the work is pure TS demux/mux of compressed samples. That is why wall is only 34.81 ms and longtasks only 173 ms: the cost is parsing EBML + emitting ISOBMFF boxes for ~770 packets, all in a tight in-process buffer pipeline.

**Why ffmpeg.wasm is slower.** ffmpeg.wasm's `remux()` (adapter.ts:2031-2069) shells the FFmpeg CLI inside the wasm VM: it writes the 4.4 MB input into MEMFS, runs `ffmpeg -i <in> -map 0 -c copy -movflags +faststart <out>.mov`, then reads the result back out of MEMFS. This is also a true stream copy (`-c copy`, no encoder), but it pays the WebAssembly tax: a full FFmpeg process bootstrap, MEMFS read/write of the whole file, and — critically — `wasmThreads` are not in play (single FFmpeg invocation), so the entire demux/mux runs as one giant synchronous wasm computation. That is why its longtasks metric is **19963 ms** of main-thread-equivalent blocking versus mediabunny's 173 ms (a ~115x gap), and its wall is 2.13x higher. ffmpeg.wasm also did not report peakMemory (n=0), so it cannot even claim a memory advantage. Its duration delta (0.005 s) is marginally tighter than mediabunny's (0.016 s), but both are an order of magnitude inside the 0.1 s tolerance, so that does not move the correctness ranking.

## What each other framework did wrong

- **ffmpeg.wasm@0.12.15** (PASS, lost on perf): correct stream-copy remux, identical oracle result (770 pkts / 475 kf / 2 tracks), but 2.13x slower wall (74.27 vs 34.81 ms), 0.47x throughput (134.93x vs 287.88x), and a ~115x worse main-thread blocking budget (longtasks 19963 ms vs 173 ms) due to wasm process bootstrap + MEMFS round-trip + single-thread synchronous execution.
- **platform@chrome-149** (NA_ENGINE): "engine does not declare operation 'remux'". Honest NA — the Chrome platform stack (MediaRecorder/WebCodecs) has no general MKV->MOV container-rewrap API, so declining the whole `remux` op is correct, not under-declared.
- **mp4box@2.3.0** (NA_ENGINE): "engine does not declare input container 'mkv'". Honest NA — MP4Box.js is an ISOBMFF-only library; it cannot parse Matroska/EBML input, so it legitimately cannot ingest the `.mkv` source.
- **remotion-media-parser@4.0.479** (NA_ENGINE): "engine does not declare operation 'remux'". Honest NA — it is a parser/demuxer, not a muxer; it has no write path to produce a MOV.
- **web-demuxer@4.0.0** (NA_ENGINE): "engine does not declare operation 'remux'". Honest NA — a demux-only library (ffmpeg-wasm-backed reader) with no mux/remux output path.
- **remotion-webcodecs@4.0.479** (NA_ENGINE): "engine does not declare output container 'mov'". Honest NA — it can write some containers but not QuickTime/MOV, so the output-container requirement (`containersOut:['mov']`) correctly gates it out. (Notably it is NOT NA on 'remux' the op nor on 'mkv' input — it declares those — so this is a targeted, plausible capability boundary, not a blanket dodge.)

## Anti-cheat validation

- **Scenario definition**: src/scenarios/remux/matrix.ts:53-60 (RemuxCase `{ asset:'h264_in_mkv.mkv', from:'mkv', to:'mov', videoCodecs:['h264'], audioCodecs:['aac'] }`), built via `buildRemuxAll` -> `buildRemux` (src/scenarios/remux/_shared.ts:84-104), id derived as `remux/h264_in_mkv_mkv_to_mov` by `remuxId` (_shared.ts:73-75). notes: "MKV->MOV: completes the MOV<->MKV arm in the reverse direction." Gating rationale (_shared.ts:25-30): for a remux op the runner only exposes `ctx.output`, so metadata/packet goldens are inapplicable; `reference-reimport` is the valid structural gate.
- **Fixture is real**: `fixtures/media/h264_in_mkv.mkv` exists, 4.4 MB (stat-confirmed). Golden `fixtures/golden/h264_in_mkv.mkv.meta.json` describes 2 real media tracks at 10.021 s; golden packets file (87 KB) exists. Not synthetic/empty/mock.
- **Winner implementation is genuine**: mediabunny `remux()` adapter.ts:1244-1260 -> `runConversion` adapter.ts:842-868 drives the real mediabunny `Conversion` API (init/isValid/execute) over the opened input and a real MOV `Output`. No canned bytes, no input->output copy, no short-circuit to the golden, no error-swallowing (invalid conversions throw). The output buffer comes from the actual muxer (`target.buffer`).
- **Oracle is meaningful**: `reference-reimport` (src/core/oracles.ts:1225-1271) re-demuxes the engine's *own output bytes* with the reference engine and, for remux, `semanticRemuxReimport` (oracles.ts:1273-1324) compares media-track count, per-type/codec track layout, and duration against the golden. It is not trivially satisfiable: an empty packet table fails (1244-1246), wrong track count/layout fails (1289-1299), and duration drift beyond max(band,0.1 s) fails (1321-1323). Measurements (770 pkts, 475 kf, 2/2 tracks, Δdur 0.016 s) are physically consistent with a 10 s 30 fps H.264+AAC clip (≈300 video frames + ≈470 audio frames ≈ 770; keyframe-heavy stream).
- **Caveat — both PASS results are cached** (`cached:true`, reason "cached previous PASS result"). mediabunny startedAtIso 2026-06-22T16:34:21Z; ffmpeg.wasm startedAtIso 2026-06-22T14:12:29Z. The evidence was reused, not re-run in this report pass; per the launcher seeding caveat, a stale PASS could in principle be reused. The oracle outputs are internally consistent and identical across engines, which is what we'd expect for a deterministic lossless remux, so staleness risk is low but non-zero.
- **Verdict: REAL** — real fixture, real library-backed stream-copy implementation, real semantic re-import oracle that can fail. (Note: the gate is structural, not bit-exact at the pixel level; it is a strong structural gate, not the strongest crypto/bit-exact rung — but for a lossless container rewrap, track-layout + packet-count + duration re-import is the appropriate and adequate correctness check.)

## Confidence & caveats

- Confidence: **high** on the winner choice. Correctness is a tie at the same oracle rung; the perf margin (2.13x wall, ~115x longtasks) is large and consistent across axes.
- Caveats: (1) perf is n=1/n=1, mad=0 by construction — single timed runs, so exact ratios carry single-sample uncertainty (the longtasks gap is so large it dominates regardless). (2) Both winners' results are cached (see anti-cheat). (3) The gate is structural re-import, not decoded-frames-bitexact; _shared.ts:19-21 explains bit-exact decode is intentionally omitted while source frame goldens are placeholders, so we cannot assert pixel identity — only structural + duration parity. (4) ffmpeg.wasm peakMemory was not captured, so the memory comparison is one-sided (mediabunny 43.70 MB measured).
