## Why the winner wins (deep technical)
The input is the hard case the scenario is built around: a `MediaRecorder`-origin WebM (`recorder_headerless.webm`, 192 KB, VP8 + Opus, encoder tag "Chrome"). A live-capture WebM is written as a single streaming Segment with **no global `Duration` element** and sparse/absent `Cues`, because at record start the total length is unknown (notes line: "MediaRecorder WebM with unknown duration / sparse Cues — duration may legitimately be null"). The golden (`fixtures/golden/recorder_headerless.webm.meta.json`) pins container=`webm`, durationSec=`3.084`, video=vp8 320x240@30fps, audio=opus 48000Hz/2ch.

Because no Segment Duration exists, the `golden-metadata` oracle does NOT apply its strict ±1-frame band to this asset. `isLooseRecorderWebm` (`src/core/oracles.ts:226-230`) matches the `recorder`/`headerless` substring in the asset id and flips the duration gate to the estimate-only loose band `max(±0.5s, ±15%)` (`src/core/oracles.ts:211-213`, applied at lines 620-625). With golden 3.084s, 15% = 0.4626s < the 0.5s floor, so the effective tolerance is **0.5s** — exactly the `durationToleranceSec=0.5` recorded in every engine's measurements. This is the technically correct call: two correct demuxers legitimately disagree on a headerless WebM's duration depending on whether they trust the last block timestamp, extrapolate the trailing frame, or include trailing audio.

That loose band is precisely what mediabunny needs. mediabunny's probe path (`src/engines/mediabunny/adapter.ts:417-453`, `metadataFromInput`) takes the **cheap-first** duration strategy: it calls `input.getDurationFromMetadata()` (line 429), which for a headerless WebM returns null/non-finite because there is no Segment Duration element to read; it then falls back to `input.computeDuration()` (line 436), which walks blocks to derive duration from the last timestamp. mediabunny's estimate lands at a `durationDeltaSec` of **0.3762s** off golden — large, but comfortably inside the 0.5s loose band, so it passes. The other four demuxers all report `durationDeltaSec ≈ 0.00017s` (i.e. they converge on ~3.0838s, essentially golden), meaning mediabunny uses a *different and looser* duration-estimation heuristic than the field. Crucially, the loose band was designed for exactly this disagreement, so mediabunny's 0.38s offset is graded as a correct estimate, not a bug — and on every non-duration field (container, track count, vp8/opus codecs, 320x240, 30fps, 48kHz/2ch) all five agree exactly ("metadata matches golden (2 track(s))").

With correctness equalized, the win is mediabunny's 11 ms wall — the fastest probe. Mechanistically that is consistent with its pure-TS ESM core (`configUsed.coreBuild: "pure-ts-esm"`, `coopCoep: "not-required"`, `sharedArrayBuffer: false`): a probe is just an EBML header read over a BlobSource, no WebCodecs/wasm warm-up on the critical path, no worker hop. The Matroska/WebML header walk to enumerate two tracks plus a block-timestamp duration estimate is the entire cost, and mediabunny's lean reader does it in ~11 ms versus ffmpeg.wasm's 192 ms (paying wasm module instantiation + libavformat probe-size scan).

- **remotion-webcodecs@4.0.479** — PASSed (durationDeltaSec 0.000173) but 30 ms (~2.7x slower). Same golden match; its convert/extract pipeline is more setup-heavy than a bare probe needs.
- **platform@chrome-149** — PASSed (durationDeltaSec 0.000173) but 31 ms (~2.8x slower). The native WebCodecs/`<video>` metadata path is correct but slower to surface track metadata for this tiny headerless clip.
- **web-demuxer@4.0.0** — PASSed (durationDeltaSec 0.000173) but 48 ms (~4.4x slower). It carries a wasm (libav-based) demux core whose init/probe cost dominates on a 192 KB file.
- **ffmpeg.wasm@0.12.15** — PASSed (durationDeltaSec 0.004) but slowest at 192 ms (~17.5x slower). Full libavformat probe under wasm: module instantiation + probe-size scan to detect VP8/Opus and estimate duration.
- **mp4box@2.3.0** — NA_ENGINE: "engine does not declare input container 'webm'". HONEST capability gap — mp4box.js is an ISOBMFF (MP4/MOV/QuickTime atom) parser and structurally cannot read a Matroska/EBML WebM container. Not an under-declared capability; it physically lacks a Matroska demuxer.

## Confidence & caveats

The winner ranking, however, rests entirely on a single cached `durationMs` per engine (n=1, no `bench`, no mad/p95), so the 2.6x margin over remotion-media-parser is suggestive, not statistically firm — a re-run could reorder the sub-30ms cluster (mediabunny 11, rmp 29, rwc 30, platform 31).

So mediabunny's "win" depends on (a) the loose gate being correct for this asset (it is, per the documented rationale) and (b) the performance tiebreak. If correctness strictness were weighted on the duration estimate, mediabunny would rank last, not first.
