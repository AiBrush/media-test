## Why the winner wins (deep technical)

**Operation & data path.** This is a true re-encode, not a remux: H.264/AAC in MP4 at 1920x1080 must be decoded, spatially resized to 1280x720, and re-encoded back to H.264 in MP4 over the full 120 s clip (`src/scenarios/transcode/index.ts:1163-1177`; `requires.features: ['resize']`, `width:1280, height:720`, `timeoutMs: 600_000`). The fixture is large (~90 MB), so this rung measures *steady-state* encode throughput, where per-frame decode→scale→encode cost dominates and init overhead is negligible.

**mediabunny's backend and code path.** mediabunny runs the entire pipeline through its `Conversion` API on the WebCodecs backend with hardware acceleration (`env.configUsed`: `backend: "webcodecs"`, `hwAccel: "prefer-hardware"`, `pipeline: "streaming-lockstep"`, `pixelBackend: "VideoSample.copyTo(RGBA)>canvas"`, `coreBuild: "pure-ts-esm"`, `coopCoep: "not-required"`, `wasmThreads: 0`). The adapter's `transcode()` opens the input, builds `ConversionVideoOptions` from the resize spec, and runs `Conversion.init/execute`, which performs read→decode→encode→mux as a single streaming pipeline (`src/engines/mediabunny/adapter.ts:1271-1322`, `runConversion` at `:842-868`). Crucially it gates the encoder config through `VideoEncoder.isConfigSupported` before committing (`:531-539`, `:651-653`) and `mb.canDecodeVideo(...)` per acceleration mode (`:888-910`), so the decode and encode legs both bind to the **Apple M1 Max hardware H.264 codec** (GPU: "ANGLE Metal Renderer: Apple M1 Max"). Hardware decode + hardware encode + GPU-side resize is exactly why a 120 s 1080p clip re-encodes in 7.62 s wall at 472 fps — the M1 Max media engine processes frames far faster than realtime (120 s of, say, 30 fps content ≈ 3600 frames / 7.62 s ≈ ~472 fps, internally consistent with the reported encodeFps).

**Oracle evidence (real numbers).** The gate is `ssim-psnr` (`src/core/oracles.ts:1688-1832`). For this resize-transcode there is no pixel-bearing golden, so the oracle uses downsampled-luma-signature SSIM with digest equality as the PSNR proxy. mediabunny scored **SSIM min 0.9999859, mean 0.9999868 over 12 frames, exactFrames 0** — i.e. its hardware-re-encoded 720p frames are perceptually indistinguishable from the reference luma signatures (well above the 0.97 floor from `tolerances`). The 0/12 digest-exact is expected and correct for a *re-encode* (a new GOP/quantizer never reproduces source bytes), which is why the scenario gates on SSIM rather than packet/byte equality.

**Why ffmpeg.wasm loses despite PASSing.** ffmpeg.wasm runs the identical logical operation through libavcodec compiled to wasm, single-thread (`adapter.ts` defaults to the single-thread core, line 10 comment; no SharedArrayBuffer/threads for this run). Its `-vf scale` path (`src/engines/ffmpeg-wasm/adapter.ts:193`) and software H.264 encode have to do all motion estimation and DCT in scalar wasm with no GPU. On a 120 s 1080p source that blows past the 300 s bench budget — the shard records `bench timeout: operation exceeded timeout of 300000ms` and an end-to-end `durationMs` of **522,626 ms (8.7 min)**. Its oracle still PASSes (SSIM 1.0000, the software encoder is high quality), but with **no bench metrics produced** it cannot compete on the scenario's primary metric. Note this large-H.264 rung is *not* in ffmpeg-wasm's budget-skip predicate (`adapter.ts:855-882` lists only `large_vp9_1080p_120s.webm` and the `h264_1080p_30s.mp4`→mkv/ts/webm cases), so the engine genuinely attempted the work and was beaten by wall time, not skipped.

## What each other framework did wrong

- **ffmpeg.wasm@0.12.15 (PASS, lost):** correctness equal (SSIM 1.0000, 0/12 exact), but its single-thread wasm software encode of a 120 s 1080p→720p H.264 clip exceeded the 300 s bench timeout (`durationMs 522,626`) and yielded **no bench metrics** — no comparable framesPerSec/wall. Loses the performance tiebreak by ~68x wall.
- **mp4box@2.3.0 (NA_ENGINE):** does not declare the `transcode` operation. Honest NA — MP4Box.js is a demux/remux/box-parsing library with no encoder; it genuinely cannot re-encode.
- **web-demuxer@4.0.0 (NA_ENGINE):** does not declare `transcode`. Honest NA — it is a demuxer only; no encode capability.
- **platform@chrome-149 (NA_ENGINE):** declared NA because the source carries an AAC audio track and its transcode path (`<video>→canvas→MediaRecorder`) cannot preserve/copy audio. Honest capability limit — canvas-capture MediaRecorder re-encode would silently drop audio, so refusing is correct rather than shipping a lossy/incomplete output.
- **remotion-media-parser@4.0.479 (NA_ENGINE):** does not declare `transcode`. Honest NA — it is a parser, not an encoder.
- **remotion-webcodecs@4.0.479 (NA_ENGINE):** declared NA because large-fixture transcodes are not reliable through its in-memory `bufferWriter` output path. This is a self-declared reliability limit on the ~90 MB fixture (the adapter notes http-range fast paths for large demux rows but not for buffered large transcodes). Plausible/honest given the in-memory writer would have to hold the whole 720p output; not an obvious under-declaration since it does declare transcode for smaller rungs.

## Anti-cheat validation

- **Scenario definition:** `src/scenarios/transcode/index.ts:1163-1177` (case `ladder_large_h264_1080p_120s_resize_720p`), built into a scenario at `:1194-1219` with `op:'transcode'`, oracle `ssim-psnr`, primaryMetric `framesPerSec`, tolerances default `{ ssimMin: 0.97, psnrMinDb: 36 }`.
- **Fixture exists & is real:** `fixtures/media/large_h264_1080p_120s.mp4` confirmed present, **90 MB** real H.264/AAC MP4 (not synthetic/empty/mock). The asset field maps directly to this file.
- **Gating oracle:** `src/core/oracles.ts:1688-1832` (`ssimPsnr`). It performs a real per-frame comparison: digest equality first, then downsampled-luma-signature SSIM gated on the **worst** frame (`minSsim >= t.ssimMin`, `:1823`). Measurements (pairs 12, SSIM ~0.99999/1.00000, exactFrames 0) are physically plausible for a hardware vs software re-encode of real media.
- **Winner adapter:** `src/engines/mediabunny/adapter.ts:1271-1322` (`transcode`) → `runConversion` `:842-868`. Genuine: it calls the real mediabunny `Conversion.init/execute` (decode→resize→encode→mux), validates `conversion.isValid` and throws on no usable tracks, gates encoder/decoder configs via WebCodecs `isConfigSupported`/`canDecodeVideo`. No canned output, no input→output copy, no short-circuit to a golden, no error-swallowing.
- **Verdict: WEAK-GATE.** The implementation and fixture are unimpeachably real (REAL on those axes), but the *gate itself* is a perceptual proxy, not a strict correctness gate: `ssim-psnr` here reports **exactFrames 0** (no bit-exact frames) and falls back to luma-signature SSIM with the PSNR gate documented as unavailable without golden pixels (`:1824-1828`). SSIM ~1.0 is strong perceptual evidence and discriminates correct vs wrong transcodes per the oracle's own comments, but it sits on the *perceptual proxy* rung of the correctness ladder, not the structural/bit-exact rung — so the PASS is genuine but not maximally strong. This does not change the winner (performance decides between two equally-proxy PASSes).
- **Cached note:** mediabunny's result is `cached: true` ("cached previous PASS result") and ffmpeg.wasm's is `cached: true` ("cached: bench timeout..."). **Staleness risk:** neither winner number was re-run in this batch; mediabunny's 7,618.85 ms wall / 472.51 fps were reused. The qualitative ranking is robust (a >68x gap cannot flip on cache noise), but the exact mediabunny throughput figures should be treated as last-good, not freshly measured.

## Confidence & caveats

- **Confidence: high** on the winner and the decisive factor. Two PASS engines, equal proxy-level correctness, and an enormous, unambiguous performance gap (mediabunny 7.62 s vs ffmpeg.wasm >300 s timeout / 522.6 s observed).
- **Caveats:** (1) Both results are cached, so absolute numbers are last-good, not fresh (ranking unaffected). (2) mediabunny's bench is **n=1, mad=0** — single sample, so the 472.51 fps / 7,618.85 ms figures carry no spread/variance evidence; treat as a point estimate. (3) mediabunny's `peakMemory` was not sampled (n=0), so memory cannot be compared. (4) The gate is a perceptual SSIM proxy with 0 bit-exact frames (WEAK-GATE), correct for a re-encode but weaker than a structural/bit-exact gate. (5) ffmpeg.wasm could plausibly PASS the oracle on a longer timeout but would still lose the throughput contest by a wide margin given single-thread wasm software H.264.
