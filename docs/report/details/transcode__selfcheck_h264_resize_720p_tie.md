# transcode/selfcheck_h264_resize_720p_tie

**Family:** transcode | **Fixture asset:** `fixtures/media/h264_1080p_30s.mp4` (31 MB, H.264 video + AAC audio in MP4) | **Primary metric:** framesPerSec | **Pass count:** 3 / 7

Operation: H.264-in-MP4 → H.264-in-MP4 transcode with a deterministic resize to 1280×720 (`options.video = { codec: 'h264', width: 1280, height: 720 }`). This is the DoD §13 self-consistency representative for `transcode` (same engine registered twice must tie within noise on frames/sec; correctness still gates the number via `ssim-psnr`).

## Verdict

- **Best framework:** `mediabunny@1.48.0`
- **Contested:** YES — 3 engines PASS (mediabunny, ffmpeg-wasm, remotion-webcodecs).
- **Decisive factor:** PERFORMANCE. All three passers clear the identical correctness gate (`ssim-psnr`, SSIM min ≈ 1.0000, 12 pairs, exactFrames=0) with no meaningful fidelity separation, so the tie is broken on the primary metric framesPerSec.
- **Margin over runner-up (remotion-webcodecs):** mediabunny 460.62 fps vs 140.79 fps = **3.27× higher throughput**; wall median 1953.9 ms vs 6392.4 ms = **3.27× faster wall**. Over the slowest passer (ffmpeg-wasm 17.96 fps / 50 105.7 ms): **25.6× faster**. Note: n=1 sample per engine (mad=0, p95==median), so the perf ordering is single-shot evidence — but the 3.3×/25.6× gaps are far larger than any plausible single-run jitter.

## Why the winner wins (deep technical)

The operation is a same-codec (H.264→H.264), same-container (MP4→MP4) re-encode with a spatial downscale 1920×1080→1280×720. Because the codec is unchanged but the resolution changes, this is a *full transcode* (decode → scale → re-encode → remux), not a stream copy; every engine must run the H.264 decoder, a resampler, and the H.264 encoder. The fixture also carries an AAC audio track, which becomes the gate that eliminates the platform engine.

**mediabunny's path (the winner).** From `env.configUsed`: `backend=webcodecs`, `hwAccel=prefer-hardware`, `pipeline=streaming-lockstep`, `coreBuild=pure-ts-esm`, `sharedArrayBuffer=false`, `coopCoep=not-required`, `canvasPoolSize=4`. The adapter drives mediabunny's high-level Conversion API: `transcode()` builds `ConversionVideoOptions` in `buildVideoOptions` (`src/engines/mediabunny/adapter.ts:546`), then `runSingle` constructs an `Output` with a `BufferTarget` and runs `runConversion` → `mb.Conversion.init(opts)` / `conversion.execute()` (`adapter.ts:848`–`855`), returning the real muxed bytes from `target.buffer` (`adapter.ts:856`–`868`). For the resize, `buildVideoOptions` sets `opts.width=1280`, `opts.height=720`, and — because both dimensions are pinned — forces `opts.fit='fill'` (`adapter.ts:586`), satisfying mediabunny's requirement that a fit algorithm accompany a width+height pair. Critically, before committing to a hardware encoder it *probes* encodability with `mb.canEncodeVideo(codec, …)` across an acceleration-mode preference list (`adapter.ts:622`–`645`); for H.264 the order is `[HW_ACCEL, 'no-preference', 'prefer-software']`, so it lands on the Apple-M1-Max VideoToolbox-backed hardware H.264 encoder (GPU line `ANGLE Metal Renderer: Apple M1 Max`). The result: hardware VideoDecoder + hardware VideoEncoder wired through a streaming-lockstep read→decode→scale→encode→mux pipeline that never round-trips through wasm. That is why it hits 460.6 fps / 1953.9 ms — the fastest path physically available in this browser for this codec.

**Correctness gate.** The gating oracle is `ssim-psnr` (`src/core/oracles.ts:1688`). A committed golden exists for this source (`fixtures/golden/h264_1080p_30s.mp4.ssim.json`, 76 KB, plus `.frames.json`), so `haveGolden=true` and the oracle compares 12 paired frames (`pairs=12`, matching the golden frame count rather than the 8-frame reference fallback). Since the output is a resize, no candidate frame is digest-identical to the 1080p golden frame (`exactFrames=0`), so the PSNR-via-digest proxy reports 0/12 exact and the gate rests on downsampled-luma-signature SSIM (`adapter.ts`/oracle lines 1773–1786). mediabunny's measured SSIM min 0.99998564 / mean 0.99998682 ≥ tolerance 0.98 → PASS. These are physically sensible numbers: a clean H.264→H.264 resize, compared against a *downscaled* luma signature of the source, should sit just under 1.0, which it does. The per-frame gate uses the worst frame (`minSsim`, oracle line 1823), so this is not a mean-smearing pass.

**Why mediabunny beats the other two passers specifically.** remotion-webcodecs also uses WebCodecs (`backend=webcodecs`, `hwAccel=prefer-hardware(+software fallback)`, `pipeline=streaming-backpressure`, `writer=bufferWriter`) and produces near-identical fidelity (SSIM min 0.99996542). It is correct but 3.27× slower (140.79 vs 460.62 fps). The gap is pipeline/throughput overhead, not a backend-class difference — both are hardware WebCodecs — most plausibly remotion's `offscreencanvas-2d` pixel backend and backpressure queue vs mediabunny's lighter `VideoSample.copyTo(RGBA)>canvas` lockstep loop with a 4-slot canvas pool. ffmpeg-wasm is the odd one out: it has the *highest* fidelity (SSIM min 0.99999689, essentially because libswscale + libx264 produce a deterministic resize), but it runs the entire decode/scale/encode in single-thread WebAssembly (no SharedArrayBuffer/threads here), so it manages only 17.96 fps / 50.1 s — 25.6× slower than mediabunny. On a tie-broken-by-perf scenario, the wasm software path cannot compete with the GPU WebCodecs path.

## What each other framework did wrong

- **remotion-webcodecs@4.0.479 (PASS, lost on perf):** Correct (ssim-psnr SSIM min 0.99996542, 12 pairs) but **3.27× slower** than mediabunny (140.79 vs 460.62 fps; 6392.4 vs 1953.9 ms wall). Same hardware-WebCodecs backend, but heavier `offscreencanvas-2d` pixel path + `streaming-backpressure` queue cost throughput. No correctness defect — pure speed gap.
- **ffmpeg.wasm@0.12.15 (PASS, lost on perf):** Correct and in fact the highest fidelity (ssim-psnr SSIM min 0.99999689) but **25.6× slower** (17.96 fps / 50 105.7 ms) because the decode→scale→encode runs in single-thread wasm (no threads/SAB in this env). Loses decisively on the primary metric.
- **remotion-media-parser@4.0.479 (NA_ENGINE):** `engine does not declare operation 'transcode'`. Honest NA — remotion-media-parser is a parser/demuxer, it has no encoder, so it legitimately cannot transcode. Not an under-declared capability.
- **web-demuxer@4.0.0 (NA_ENGINE):** `engine does not declare operation 'transcode'`. Honest NA — web-demuxer is a demux-only library (no encode path).
- **mp4box@2.3.0 (NA_ENGINE):** `engine does not declare operation 'transcode'`. Honest NA — MP4Box.js is a box parser/muxer with no video codec, so transcode is genuinely out of scope.
- **platform@chrome-149 (NA_ENGINE):** `transcode is NA — the source fixture carries audio and the MediaRecorder canvas-capture path cannot preserve or copy audio` (durationMs=2, declined in pre-flight). This is an honest capability NA: the platform engine's encode path is `<video>→canvas→MediaRecorder`, which can re-encode video pixels but has no way to carry the existing AAC track through unchanged, so it correctly declines an A/V transcode rather than silently dropping audio.

## Anti-cheat validation

- **Scenario definition:** `src/scenarios/transcode/index.ts:1704` (id `transcode/selfcheck_h264_resize_720p_tie`), `input: 'h264_1080p_30s.mp4'`, `op: 'transcode'`, `options.video = { codec:'h264', width:1280, height:720 }`, `oracles: ['ssim-psnr']`, `tolerances: { ssimMin: 0.98, psnrMinDb: 38 }`. Notes (line 1720) confirm the intent: DoD §13 self-consistency, "correctness (ssim-psnr) gates the number."
- **Fixture exists & is real:** `fixtures/media/h264_1080p_30s.mp4` — 31 MB, real H.264+AAC MP4 (committed golden `fixtures/golden/h264_1080p_30s.mp4.ssim.json` 76 KB and `.frames.json` 3.2 KB also present). Not synthetic/empty/mock.
- **Winner adapter is genuine:** `src/engines/mediabunny/adapter.ts:1271` (`transcode`) builds real `ConversionVideoOptions` (`adapter.ts:546`), opens the input, creates an `Output`+`BufferTarget`, and at `adapter.ts:848`–`855` calls `mb.Conversion.init` then `conversion.execute()`, returning the actual muxed buffer (`adapter.ts:856`–`868`). It probes the encoder with `mb.canEncodeVideo` (`adapter.ts:638`). No canned output, no input→output copy, no short-circuit to the golden, no swallowed errors (it throws on invalid conversion / unencodable codec).
- **Oracle is meaningful:** `src/core/oracles.ts:1688` (`ssimPsnr`). It re-decodes the candidate output and pairs 12 frames against the committed golden, computing per-frame downsampled-luma SSIM and gating on the **worst** frame (`minSsim >= t.ssimMin`, line 1823). Measurements are plausible: 12 pairs, exactFrames=0 (expected for a resize — pixels differ from the 1080p golden), SSIM min/mean just under 1.0.
- **Caveat — this is a proxy gate, not bit-exact:** PSNR via golden pixels is unavailable (golden ships luma signatures, not raw pixels), and the digest-exact count is 0/12, so the PASS rests on perceptual SSIM ≥ 0.98 rather than a bit-exact or true-PSNR comparison. SSIM ≈ 1.0000 against a downscaled-source signature is reassuring but is the weakest correctness rung (perceptual proxy). The ssimMin tolerance for this scenario (0.98) is loose enough that fidelity does not separate the three passers — which is *why* the tie correctly falls to performance.
- **Cached note:** All three PASS results have `cached: true` ("cached previous PASS result") — they were reused, not freshly re-run. Per the launcher-seeding caveat, cached PASS reuse carries staleness risk; the perf numbers (and the SSIM values) are from a prior run, not this invocation.
- **Verdict:** **WEAK-GATE.** Real fixture + genuinely implemented winner (real mediabunny Conversion + WebCodecs hardware encode) + a real comparison oracle — but the gate is an ssim-psnr *proxy* with exactFrames=0 and a 0.98 SSIM tolerance, i.e. perceptual-only, not bit-exact/structural. The PASS is real; the gate is not the strongest available rung. Combined with cached==true on all passers, confidence in the exact perf magnitudes is tempered, though the ordering is unambiguous.

## Confidence & caveats

- **Confidence: medium.** The winner ordering is clear-cut (3.27× and 25.6× perf gaps, all on the same correctness gate), but two factors hold it back from high: (1) every result is `cached==true` (reused, not re-run this session), and (2) every bench metric is n=1 (mad=0, p95==median), so there is no spread evidence — a single-shot perf comparison. The gaps dwarf plausible jitter, so the conclusion holds.
- The correctness gate is a perceptual SSIM proxy (exactFrames=0, no true PSNR, tolerance 0.98), so this scenario does not establish bit-exact transcode fidelity for any engine — only that all three produce perceptually faithful 720p output.
- `throughputRealtime`, `peakMemory`, and `longtasks` were not recorded in this shard's bench, so memory/longtask tiebreakers could not be applied; framesPerSec/wall were sufficient and decisive.
- This is a self-consistency (register-twice tie) representative; the design intent is that perf is the headline number and ssim-psnr merely guards it — consistent with the perf-driven verdict here.
